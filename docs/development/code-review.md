# Bubu AI · Code Review 规范

评审以 **功能正确、文件安全、代码边界、可维护性** 为先，视觉还原其次。每个 PR 必须由人审核；Codex 的自检不能替代你的最终审核。

## 必查项

1. **范围**：只改当前 Issue，未顺手加入无关功能、架构、依赖、大规模格式化、任务日志 MD。
2. **正确性**：验收标准逐项满足，真实操作结果来自系统而非模型猜测，错误/空值/取消/重复请求有处理。
3. **权限**：Electron IPC 参数校验，默认最小授权；敏感路径、符号链接逃逸、文件冲突、防覆盖、授权撤销、云端正文发送都按当前功能覆盖。
4. **状态一致性**：任务状态来自 Run Event，列表、进度、审批和结果有明确来源；无法量化不显示假百分比。
5. **前端**：类型安全、职责单一、组件可复用、请求取消与卸载清理、长列表性能、键盘与无障碍、UI Token 一致。
6. **Agent**：工具 Schema 校验、超时/取消、模型能力检测、不信任读取文件的“指令”、限制循环步数和工具副作用。
7. **数据与凭据**：Key 不进入 UI 状态快照/普通日志，用户文件正文最小外发，SQLite/本地数据不误入 Git。
8. **测试**：覆盖正向和反向，关键场景有可重复的 fixture；UI 改动有截图，所有声明通过的命令可复现。
9. **文档**：修改原有稳定文档，未实现能力仍标 `planned`，不创建 A01/B01 之类的任务总结。

## Review 反馈等级

- **Blocker**：越权、误删/误覆盖、敏感数据泄露、严重状态错误、不能启动。
- **Major**：功能错误、无关键测试、容易导致重复执行、架构边界不清晰。
- **Minor**：可维护性、命名、性能、交互小问题。
- **Suggestion**：改善体验但不阻塞当前 Issue。

## 完成后 Codex 必须提交的 Review 摘要（写在回复 / PR，不单独建文件）

```text
目标 Issue：#... 
改动概要：...
主要修改文件：...
运行验证：pnpm ...（真实结果）
未验证：...（如有）
已知风险：...
需要用户检查：...
是否修改既定范围：否 / 是，原因 ...
```

对于不涉及文件权限的普通 UI PR，无须强行补一整套文件系统安全测试；但不允许因此绕开新暴露的 IPC 权限边界。
